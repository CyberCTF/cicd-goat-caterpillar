# Upstream

This lab reproduces one challenge — **Caterpillar** — from CI/CD Goat.

| What | Source | Licence |
| --- | --- | --- |
| The "Caterpillar" challenge (public / fork-based Poisoned Pipeline Execution, 3PE, against a Jenkins pipeline) | [CI/CD Goat](https://github.com/cider-security-research/cicd-goat) by Cider Security (now Palo Alto Networks), v1.2.7 | Apache-2.0 |
| Security class | [OWASP CICD-SEC-4: Poisoned Pipeline Execution](https://owasp.org/www-project-top-10-ci-cd-security-risks/CICD-SEC-04-Poisoned-Pipeline-Execution) | — |

Only the *vulnerability* is reproduced, not upstream's eight-machine CI/CD stack. The lab is two
machines — a Jenkins controller and a Gitea git host — which is the minimum this attack needs: a
public repository whose pull requests (including those from forks) are built by CI, a write-scoped
token exposed to those builds, and a credential a second, more-trusted pipeline can read.

Nothing is vendored from upstream. Upstream serves a copy of a third-party project as the
`caterpillar` repository and bakes a fixed flag into Jenkins. This lab instead ships an **original**
minimal sample package (`build/gitea/repo-src/`, authored here, no third-party code) with an original
`Jenkinsfile`, and injects a **per-player** flag into the Jenkins credential store at run time, so
each player exfiltrates their own flag and nothing but the challenge idea comes from upstream.

## The two-stage attack (what makes it *public* PPE)

Direct PPE assumes the attacker already has write access. **Public / fork-based PPE (3PE)** does not:
the attacker holds only a plain account. The faithful chain, which both the player and the solver
walk, is:

1. **Fork** the public repository (no write access required) and change its `Jenkinsfile` to dump the
   build environment (`sh 'env'`).
2. **Open a pull request** into `main`. The test pipeline builds the pull request — *including from a
   fork* — and prints the environment, where the write-scoped `gitea_token` is exposed.
3. **Escalate**: re-clone the original repository with the stolen token, poison the `Jenkinsfile` to
   bind the `flag2` credential, and push to `main`; the prod pipeline runs it and exfiltrates the
   flag.

The escalation is load-bearing: `flag2` is scoped to the prod pipeline's folder, so the untrusted
fork-PR build cannot bind it. Only pushing to `main` (which needs the stolen write token) reaches a
pipeline that can.

## Faithful deviations

### The trigger — git multibranch poll, not the Jenkins Gitea plugin

Upstream wires the trigger with the Jenkins **Gitea** plugin (a Gitea SCM source that discovers pull
requests, with a periodic rescan). This lab uses the core **git** plugin's multibranch source with
its *"discover other refs"* trait (`refs/pull/*/head`) and the same one-minute periodic rescan (an SCM
poll, no inbound webhook). Gitea publishes a `refs/pull/<n>/head` ref in the **base** repository for
every pull request, including cross-repository (fork) ones, so the git plugin discovers and builds the
fork's code without a Jenkins↔Gitea plugin version dependency — which matters for a lab family meant
to run unattended. The attack and the player's steps are identical: fork, poison the `Jenkinsfile`,
open a pull request.

### The token form

Upstream's `gitea_token` is a Gitea personal access token used as `http://<token>@host/...`. A real
PAT is generated by the server at run time and cannot be baked into the image, so this lab exposes the
write CI robot's basic-auth push credential in the same single-field form: `gitea_token` is
`hatter:<password>`, used as `http://$gitea_token@host/...`. It is genuinely write-scoped (the `hatter`
robot is a write collaborator) and is leaked to pull-request builds exactly as upstream's token is.
It is infrastructure, not the per-player flag.

### The exfiltration encoding (masking)

Upstream's solution prints `echo $flag2 | base64`, relying on base64 slipping past credential masking.
On the modern Jenkins this lab ships, the `credentials-binding` plugin masks a bound secret's raw
value **and its plain base64**, so that exact trick no longer works. The lab keeps the vulnerability
identical (a credential a pipeline binds) and only updates the encoding the attacker uses to one the
masker does not precompute — reversing before base64 (`echo $flag2 | rev | base64`). This is arguably
a truer lesson for current CI: masking is a best-effort guardrail, not a control, and a chosen
transform defeats it.
